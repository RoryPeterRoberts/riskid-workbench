# dsh-superagent-prototype against our build route (checked 3 November 2026)

Repository: github.com/deepseek-ai/dsh-superagent-prototype, "Towards a More Autonomous Agent System", MIT, TypeScript, published 31 October 2026 (one commit), 16,102 stars by 3 November. The README calls it a research prototype, not an official product, adapted from an internal version and not identical to the design article.

**What it is.** A proactive coding agent for one GitHub repository, packaged as a DeepSeek Harness bundle. Sources (GitHub notifications, issues, pull requests, CI; optionally Feishu chat) produce Triggers; a Policy (allowed senders, rules) turns authorised requests into Tickets; each Ticket runs in its own dsh Executor Session and its own directory (a git worktree made by a prepare command), under a worker preset whose shell moves commands to background jobs after 5 seconds and may spawn subagents; the worker reports ready / blocked / failed / waiting / dropped; a router session routes follow-ups; delivery is a pull request, with auto-merge allowed only under written delivery requirements (default: under 200 lines, approvals covering the head commit, never as the agent account); a web panel lists only what needs a person. Background work has 30 minutes per turn; a concurrency limit governs worker slots; failures retry three times on provider or network errors, then hold for a person.

**Philosophy** (docs/000): take as little human attention as possible; act only when asked or when a written rule allows; speak only when a person must act or can use a result; one concrete question at a time; stop by impact, not effort; report honestly, a draft marked unfinished.

**Fit with the RiskID Workbench plan.** Strong in shape. PLAN.md's rounds map onto Tickets one to one: an issue per round, a worktree per ticket, tests run as background jobs, a PR per round, Rory as the reviewer and merger. That is the fresh-session-per-round with an immutable objective and a bounded handoff that today's measurements favour, with the GitHub workflow and the attention-minimising panel on top. The prompts (orchestrator, worker, handoff: 159, 138 and 120 words) are short and reusable; the worker prompt's "finish focused changes; pause with an incomplete draft only for the conditions it names; distinguish completed work from an incomplete draft" is the stop rule we want.

**What it needs on this machine.**
- dsh `^0.2.1-alpha.2`; installed here is 0.1.1-rc.2. An upgrade touches the frozen production profile unless 0.2.1 is installed under a separate npm prefix and used only by a separate `superagent` profile (the guide requires a dedicated profile anyway).
- Node 22.19+ (have 22.23), pnpm (9.0), git 2.32+ (2.43), tmux (3.4), Python 3.8+, GitHub CLI 2.48+ (have 2.45, upgrade needed).
- A dedicated GitHub user account for the agent with write access to the repository (a GitHub App cannot be used: it reads the account's notifications), and the repository on github.com. The workbench is open source, so a public repository is the plan anyway. DeepResearch is unaffected and stays unpushed.
- A model provider configured in the profile: the local Qwen through the guard works in principle; the worker role (background jobs, subagents, structured reports) is heavier agentic behaviour than measured today, and the router's judgments are policy-driven rather than model-driven, which suits E5-pre's finding.

**Risks.** Three days old, one commit, "may still contain bugs". The dsh version jump. Qwen as worker under a 5-second foreground shell and job-completion messages is untested here. Feishu parts are irrelevant.

**Recommendation.** Worth a trial, in a separate profile with its own dsh 0.2.1 install, on the new `riskid-workbench` repository, with PLAN.md round 0 as the first issue. About half a day of setup (the repository, the agent account, the gh upgrade, the profile, the prepare command). Judge it on round 0 to round 3: does a ticket end in a mergeable PR with green tests without Rory's attention between the issue and the review. If not, fall back to dsh's own goal rounds and plan mode in the production profile.
